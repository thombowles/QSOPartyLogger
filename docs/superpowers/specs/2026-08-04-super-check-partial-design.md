# Super Check Partial — design

**Date:** 2026-08-04 · **Status:** approved for implementation

## What and why

Super Check Partial (SCP) is the contest-logger convention of showing, while a
callsign is being typed, every known contest call that contains the typed
fragment — so `N5K` surfaces `N5KO N5KW W5NK…` before the station has finished
identifying, and a busted copy shows itself as a call the database has never
heard of. The database is the community `MASTER.SCP` file: ~50,000 calls
distilled from submitted contest logs, published at supercheckpartial.com.

Tom's requirements, verbatim in scope:

1. Matching calls are displayed while typing, **as an option** the operator can
   turn off.
2. The app checks for and downloads `MASTER.SCP` itself **at an intelligent
   time** — never a manual download, the same stance the app already takes for
   cty.dat (`DXCCLabelClient`) and call history files (`CallHistoryClient`).

## Upstream, verified 2026-08-04

- URL: `https://www.supercheckpartial.com/MASTER.SCP` — served over valid TLS
  (BunnyCDN), so no ATS exception is needed. HEAD answers with
  `Last-Modified` (`Fri, 31 Jul 2026 00:03:08 GMT` at fetch) and
  `Content-Length: 359507`.
- File shape, from the live file: one `!!Order,1,1` directive line, `#` comment
  lines carrying `# Release 2026.07.31` and `# Generated by bb-scp`, then one
  uppercase callsign per CRLF line, charset `[A-Z0-9/]`. 50,020 calls.
- The in-file `# Release` date matches the server's `Last-Modified` date, so
  Last-Modified is a truthful freshness token and a HEAD can judge staleness
  without downloading the body — exactly the cty.dat situation.
- **Hint data, never authority** (constitution Article 1): SCP is a
  community-compiled roster. Nothing from it reaches scoring, validation, or
  export; it only draws grey text on screen.

## Architecture — three units plus wiring, all existing patterns

### `SCPDatabase` (Sources/Core/CallHistory/)

Value type: parse + match, no I/O.

- `parse(data:) -> SCPDatabase?` — decode UTF-8 (isoLatin1 fallback), keep
  tokens matching `^[A-Z0-9/]{3,}$` after trimming (drops the `!!Order`
  directive and `#` comments naturally), uppercase, dedupe, sort. Captures the
  `# Release …` comment when present, for status display only.
- `matches(for:limit:) -> Matches` — fragment normalized uppercase; empty
  below `minimumFragmentLength = 3` (two characters match thousands of calls
  and mean nothing yet). Containment match, ranked: exact call first, then
  calls starting with the fragment, then the rest containing it, alphabetical
  within each tier. `Matches` carries the capped list plus the total, so the
  UI can say `+N more` truthfully.
- `minimumRecords = 1000` — the floor an installed file must clear. The real
  file has ~50k calls; an error page, truncation, or lookalike will not
  produce 1000 tokens that scan as callsigns.
- A linear scan over 50k short strings is single-digit milliseconds and runs
  once per keystroke (in `EntryFlow`), never per render. No index structure
  until profiling says otherwise.

### `SCPStore` (Sources/Core/CallHistory/)

`CallHistoryStore`'s shape, verbatim: `MASTER.SCP` exactly as served plus a
`MASTER.meta.json` sidecar in
`~/Library/Application Support/QSOPartyLogger/SCP/`, atomic writes, a missing
sidecar never hides a readable file. Meta: `sourceLastModified` (the server's
header string — the freshness token), `fetchedAt`, `lastCheckedAt` (the
throttle clock, advanced by every check including ones that download nothing).

### `SCPClient` (Sources/App/)

`DXCCLabelClient`'s decision loop, adapted to a file that is itself the
payload:

- `SCPFetching` seam (`head`/`get`, its own protocol like every other client;
  `LiveSCPFetcher` is the only network code and is never touched by tests).
- `refreshIfStale(now:force:)`: 24 h throttle off `meta.lastCheckedAt`;
  `force` is the Refresh button.
- **With a cached file:** HEAD, parse both dates, download only when upstream
  is strictly newer — a mirror or clock going backwards must not roll the
  database back. No `Last-Modified` in the answer → quiet failure, cache
  stays (freshness cannot be judged; blind downloads are the worse error).
- **With no cached file (first launch):** straight to GET — there is nothing
  to compare against and nothing to protect, and a HEAD first would just be a
  second request. This is what makes the feature zero-setup.
- Verify before install: not an HTML page in disguise, parses, and
  `recordCount >= minimumRecords`. A refused file leaves the cache in
  service.
- Quiet by construction, like the other three clients: status enum
  (`idle/checking/downloading/ready/failed`), `lastError`, capped console.
  A failure never reaches the entry path.
- `onDatabase: ((SCPDatabase) -> Void)?` publishes the parsed database —
  cached at activation, downloaded when installed.

### The intelligent time

Same triggers as the DXCC check, same reasoning: **at launch and at every
contest load**, throttled to one check a day, cached copy published instantly
and unconditionally. The entry path never triggers network. Opening six logs
in an afternoon makes at most one HEAD; the ~360 KB body moves only when the
release actually changed (upstream re-releases every few weeks). Launching on
contest morning is exactly when a newer file is wanted, so there is no
contest-window special case — the download is a third of a megabyte and
installs atomically off the entry path.

### Wiring (`EntryFlow`, `MainView`)

- `EntryFlow.updateSCPDatabase(_:)` stores the database (or nil when the
  toggle goes off) and recomputes; `callChanged`/`stationChanged` refresh
  `scpMatches` alongside the existing prefill refresh. Matches live on the
  flow, computed once per call-field change — the view only reads them.
  The existing `.onChange(of: entry.call)` already fires for programmatic
  clears (logging a contact empties the field), so matches cannot outlive
  the call they belong to.
- `MainView.activateSuperCheck()` mirrors `activateCallHistory()`: clear,
  gate on the setting, publish cached, kick `refreshIfStale` in a background
  task. Runs at appear, at party change, and when the toggle flips.

### `SuperCheckRow` (Sources/UI/)

A single fixed-height strip directly under the entry bar: monospaced call
chips, the exact match tinted green (the eye's "known call" confirmation),
`+N more` when the cap (24) is exceeded. Two deliberate choices, both with
house precedent:

- **Reserved height while the feature is on** (setting enabled and a database
  loaded): the strip is present even when empty, because it fills and empties
  on every keystroke — the `WorkedBeforeTable` height arithmetic exists
  precisely so mid-run layout never jumps, and a strip that reflows the
  window at 35 WPM would be worse than 22 px of quiet. With the setting off
  (or no database yet), the row is absent entirely.
- **Not interactive**, like `WorkedBeforeTable` rows: a click target directly
  above the log table is a mis-click hazard mid-run, and the operator is
  already typing the call — the strip is for the eye. (Article 7 is
  satisfied: the display has no controls, and its option is an ordinary
  toggle, keyboard-reachable in Contest Setup.)

### The option (`AppSettings`, `SetupSheet`)

`superCheckEnabled`, default **on** (the house default for assistance that
costs nothing until consulted — `callHistoryEnabled`, `hubSpotsEnabled`), off
with one toggle. A global row in Contest Setup beside the call history row —
same anatomy: toggle, status line (release + call count, or the error), and a
Refresh button that bypasses the throttle. SCP is not per-party, so the row
does not hide with the party.

## Failure posture

The feature is a convenience shell around a cache: no network, no file, or a
refused download all degrade to "the strip shows nothing" or "the strip shows
last release's calls", never to an error in the entry path. Status and errors
land in the Contest Setup row and the client console, inline, matching the
call history row (no modal alerts).

## Testing (Article 5: no network, no real preferences)

- `SCPDatabaseTests` (Core): parsing the real file's shapes — directive line,
  comments, CRLF, dedupe, garbage tokens, isoLatin1 bytes; release capture;
  match semantics — minimum fragment, tier order (exact / prefix /
  containment), alphabetic within tier, cap + total, no matches below floor.
- `SCPStoreTests` (Core): round trip, sidecar, missing-meta tolerance,
  `touchLastChecked`, temp folders only.
- `SCPClientTests` (App): scripted `SCPFetching` — unchanged release downloads
  nothing; older upstream ignored; six triggers in a day make one check;
  first launch downloads without a HEAD; missing header with a cache fails
  quietly, without one downloads anyway; HTML masquerade and short files
  refused with cache kept; a real install publishes the database and stamps
  meta; `force` bypasses the throttle.
- `EntryFlow` tests (App): matches follow the fragment as it grows and
  shrinks; a late-arriving database populates matches for the fragment
  already typed; removing the database (toggle off) empties them; logging a
  contact leaves no stale strip.

## Alternatives considered

- **Bundle a MASTER.SCP snapshot** for offline first launch: rejected — 360 KB
  of data in the repo that ages every few weeks, against the call-history
  precedent (download-and-cache, nothing bundled). First launch without
  network shows no strip until the first successful check; nothing else
  degrades.
- **Reuse `CallHistoryStore`** keyed by a pseudo-party id: rejected — the
  store's key is a party and SCP is global; a fake key is a lie that outlives
  its convenience.
- **A trie/index for matching**: rejected for now — the linear scan is
  milliseconds at this size, runs off the render path, and the index would be
  the only clever data structure in the codebase.

## Decisions taken without Tom (autonomous session), lowest-risk defaults

1. Default **on** — matches every peer toggle; the option exists as asked.
2. Minimum fragment **3** — named constant, trivially changed.
3. Display cap **24 + "+N more"** — named constant in the row.
4. The strip is display-only in v1 — no click-to-fill, no keyboard cycling;
   both are additive later if wanted.
5. Release-date surfacing uses the server's `Last-Modified`/in-file
   `# Release` for the setup row's status only; freshness logic never parses
   the body's comment.
